# 对比:code-review-graph 交叉分析

`~/Projects/code-review-graph`(下称 **CRG**,Python)和本仓(**CodeGraph**,TypeScript)是什么关系?一句话:**同一家餐厅的两种经营模式**。后厨几乎一样——都用 tree-sitter 把代码切成语法树、都存进 SQLite、都在本地跑、都通过 MCP 端菜给 AI agent。但一家做的是"帮厨师边炒边查菜谱"(CodeGraph,服务*写代码*的时刻),另一家做的是"菜品出厂前的质检报告"(CRG,服务*审代码*的时刻)。

这一章不罗列功能表。我们挑四个具体问题,看两家餐厅各自怎么上这道菜——差异自然就浮出来了。

## 问题一:"我改了这个函数,会炸到谁?"

这是影响分析(impact analysis),两边都有的功能,但算法形状完全不同。

CodeGraph 的答案像**顺着水管倒着摸**:从函数节点出发,沿着"谁调用了我"的边一层层往外爬(BFS),爬到哪算哪。它的实现(`traverseBFS`)里最费心思的是防重复:同一条边可能被两端各遇见一次,要按 `source|target|kind|line|col` 五元组去重;一个热门函数有一百个调用者时,邻居要一次性批量取回而不是查一百次库。

CRG 的答案像**给水管的每段标了漏水量**:它不数跳数,而是给每种边定权重(CALLS 边 1.0 分、INHERITS 继承边 0.9、TESTED_BY 0.7…),每往外爬一跳分数乘 0.6 衰减,最后给你一个**总分**。而且它默认不用内存图库(networkx 只是备胎),而是把整个 BFS 写成 SQL 在临时表里迭代——图再大也不占内存。

同一个问题,两种输出形态:**路径列表**(哪些文件、哪些行)vs **风险分数**(0 到 1 的一个数)。为什么?因为下一个消费者不同——CodeGraph 的分数要喂给 agent 的眼睛(它要看具体位置才能去验证),CRG 的分数要喂给 CI 门禁(`fail-on-risk`,超过 0.70 直接让 PR 不过)。**输出跟着消费者走,这是一切差异的总纲。**

## 问题二:"这个按钮点击之后到底调用了什么?"

这是全书反复出现的动态分发问题,也是最能看出设计品味的地方。看这段真实的代码:

```ts
class TaskRepository {
  onChange(cb) { this.listeners.add(cb); }        // 注册:把回调存起来
  notifyChange() { for (cb of this.listeners) cb(); }  // 触发:挨个调用
}
taskRepo.onChange(logCompletion);   // 接线:在这里发生!
```

`notifyChange()` 调用 `logCompletion` 这件事,**语法树上根本不存在**——AST 只能看到"遍历集合并调用元素"。静态解析到这里必然断链。两家怎么补?

**CodeGraph 的办法:事后扫描 + 记录案发现场。** 建完图后,36 个"合成器"逐个扫图,认名字:`onChange` 匹配 registrar 约定(以 on/addListener/subscribe 开头),`notifyChange` 匹配 dispatcher 约定(含 notify/emit/fire),然后去注册行的源码里正则捕获实参名 `logCompletion`,凭空造一条边:

```
notifyChange ──calls──▶ logCompletion
   标注:synthesizedBy=callback, registeredAt=src/server.ts:5
```

精髓在 `registeredAt` 这个标注——它记下了"这条边是在第 5 行接上的"。当 agent 半信半疑想验证时,直接看第 5 行就行,不用再去 Grep 全仓库找证据。(本书实证篇做过完整实验:方法名改成 `addChangeListener` 这种不在约定里的名字,合成器会**静默拒绝工作**——宁可断链不可造假边。)

**CRG 的办法:给事件本身发身份证。** 它不是在两个函数之间拉线,而是造一个虚拟的中间节点:

```
publishEvent() ──▶ [Event: task_completed] ◀── onTaskCompleted()
```

Spring 的事件总线、Temporal 的工作流、DI 容器的注入(INJECTS 边)都是这个思路。好处是事件成了可查询的实体("谁在监听 X?"是一个模式查询);代价是你没法把它当成一条连续的调用路径念出来。

一个是**侦探式**(还原案发过程),一个是**户籍式**(建立登记制度)。如果你的下游是 agent 的 trace 叙事,前者顺手;如果是架构审计报表,后者整齐。

## 问题三:"帮我找处理登录的代码"

注意这个问题里没有出现任何标识符——没有函数名、没有类名,是纯人话。这恰好打在两家的能力盲区互补处。

CodeGraph 的检索栈是 **FTS5 单路做深**:全文索引只认词,"处理登录的代码"拆出来的中文词在标识符世界里颗粒无收。它的补救是把检索做成四级瀑布(FTS 不中→LIKE 子串→编辑距离模糊→精确名补充),外加一张"驼峰拆词表"——把 `handleLoginAuth` 拆成 handle/login/auth 存进辅助表,这样搜 "auth" 能命中驼峰名。但前提仍是:**查询里得有英文词**。

CRG 加了一条向量通道:可选安装 sentence-transformers,把每个符号的名字+签名+文档编码成语义向量,搜索时做相似度匹配。"处理登录的代码"在语义空间里离 `authenticateUser` 就近了很多。代价也直白:多一个几百 MB 的模型依赖,云厂商 API 还会把你的代码文本发出去(CRG 为此专门做了出口告警)。

所以这里有一条清晰的互借清单:CodeGraph 缺语义搜索(它赌的是"MCP 指令能把 agent 教得会用符号名提问"),CRG 的 extras 可选依赖模式值得抄;而 CRG 的 FTS 权重偏心(name 列权重 20 压倒 docstring 的 1)这类细节,双方其实已经互相趋同。

## 问题四:agent 打开门的那一刻

两个项目对"agent 会怎么用我"做了**相反的赌注**,这是全篇最深的一条裂缝。

CodeGraph 的实验记录里写着一条血泪结论:往 MCP 指令里写"请先用 trace 工具"、换三种措辞、加示例——**全部无效**,agent 该怎么干还怎么干,墙钟时间甚至变差了。于是它走向减法:默认只暴露**一个**工具(`codegraph_explore`),把 flow 检索、路径构建、源码内联全部塞进这一次调用里;错误响应永远伪装成成功(实测 agent 收到两次报错就会整个会话弃用你);输出预算随仓库规模单调递增,且绝不超过 host 的内联上限——超了会被转存成文件,agent 又得读一遍,前功尽弃。

CRG 走的是相反的加法:**30 个工具、5 个提示模板**(review_changes/debug_issue/onboard_developer…)、每个响应末尾带 `next_tool_suggestions` 字段主动推荐下一步、随包分发 7 个 Claude skills 当操作手册。最激进的一招是一个 PreToolUse hook:**拦截 agent 发起的每一次 Grep/Glob/Read,在它执行前往结果里注入图的上下文**——等于不等客人点菜,直接往菜里加料。

哪个对?诚实地说:**取决于宿主 agent 听不听话**。强模型的工具选择能力好,货架式(30 个工具)反而灵活;弱模型面对一堆工具会平均用力,专家柜台式(1 个工具)才保得住采用率。CodeGraph 刻意用 Sonnet 这种"地板模型"做验证,就是赌用户手里的 agent 大多是弱的;CRG 的目标用户(跑 PR 流水线的团队)场景更固定,hook 拦截可控性更高。两条路线还没有公开的正面交锋数据。

## 数据模型:5 种积木够不够?

前面四个问题看完了,回头看一个基础分歧,现在它好理解了。

CodeGraph 有 **23 种节点类型**(file/class/method/route/component/union…),CRG 只有 **5 种**(File/Class/Function/Type/Test)。乍看 CRG 太糙,但换个问法:它的查询需要吗?它的 17 种图模式(谁调用它/谁测试它/谁监听它/谁消费它…)在 5 种积木上全能表达,而 Test 作为独立种类直接进了风险公式("测试缺口占 0.30 权重")——**它不需要知道什么是 route,因为它的 17 种查询模式没有一个问得到路由**。

反过来,CodeGraph 没有 Test 类型,但 explore 输出里那句 "no tests found within 3 caller hops" 已经暴露了需求——只是它的解法是靠路径降权(test 目录 ×0.3)而非建类型。**类型系统是查询需求的投影**,这句话是读懂一切 schema 设计差异的钥匙。

## 最后:工程性格

日常相处下来,两个仓库的性格差异比技术差异更鲜明。

翻 CodeGraph 的代码,到处是这种注释:"仅靠 visited 守卫入队会让经两条平行边的目标被排队两次(#1090)"——**每个防御性写法都挂着一场事故的编号**,像是把 bug 报告钉在了案发现场。翻 CRG 的代码,看到的是另一种清单:"禁止 eval/exec/pickle、subprocess 一律 list 参数、所有返回给 MCP 的名字必须过 `_sanitize_name` 剥控制字符(256 字符上限,防 prompt 注入)"——**它防御的不是自己的历史失误,而是送进渲染管道的不可信输入**(review 场景天生要吃别人的 diff)。

一个向后看(每行代码都有来历),一个向外看(每个入口都有门禁)。遥测的选择也是同构的:CodeGraph 做 opt-in 遥测研究用户怎么用产品;CRG 一行遥测都没有,唯一的网络出口是用户显式配置的 embedding 服务。两种性格没有高下,但决定了两个项目各自会在哪里摔倒、在哪里长出铠甲。

## 选型速断——以及"都装"的真实代价

- 你要**边写代码边问结构问题**(callers、trace、impact,agent 在循环里高频调用)→ CodeGraph,它是为这个循环调的音;
- 你要**审 PR、管风险、留档架构**(CI 门禁、PR 评论、wiki、社区检测、跨仓库)→ CRG,这条流水线上它样样齐备。

那,两个都装?上一版这里写的是"数据目录互不冲突,可以同时装"——技术上没错,但对 LLM 来说是个坏建议,值得把代价摊开算一遍:

1. **工具面就是常驻上下文。** MCP 的工具定义挂在会话的 tools 列表里,每一轮都在场。30 个 CRG 工具加一套 CodeGraph 工具,等于让 agent 每句话开口前先背两份菜单;
2. **语义重叠制造选择竞争。** 同一个影响分析问题现在有两个入口(`get_impact_radius_tool` 和图遍历类工具)、两种输出形态(分数 vs 路径)。本章开头引用过的实验结论恰好在这里反噬:选项越多,agent 越平均用力,采用率反而下降——CodeGraph 砍到只剩一个工具就是为了治这个病;
3. **指令打架。** 两家都在 initialize 响应里注入自己的世界观(CRG:"永远先查图再 Grep";CodeGraph:"别指望指令改变 agent 行为,答案要完整到让它停手")。单看各自成立,合在一起是两套互相竞争的行为学;
4. **两份索引,两种陈旧。** 同一仓库两套 watcher、两套 staleness 标记。agent 从一边读到"新鲜"、另一边读到"过期"时,没有机制告诉它该信谁。

所以现实的最优解是**按时刻分配,而不是按工具堆叠**:

- **编码会话**:只挂 CodeGraph——它默认一个工具的姿态本来就是为共存优化的;
- **PR 审查**:走 CRG 的 GitHub Action 形态。这是它最干净的存在方式——根本不占用任何交互会话的工具位,风险报告以评论形式出现,agent 与人都不需要实时付注意力税;
- **确实要在同一会话共存时**:CRG 支持 `CRG_TOOLS` 白名单裁剪,把它缩到 `detect_changes` + `get_review_context` 两三个评审专属工具,与 CodeGraph 的检索职责零交集,并在项目指令里明文分工——即便如此,也只是"可忍受"而非"推荐"。

一句话:**对 LLM 而言,"能装"和"该装"之间隔着整个注意力经济学。** 工具数量的每一次增加都是在向所有其他工具借注意力,而这笔债是按轮计息的。
