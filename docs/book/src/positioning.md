# 定位与使用场景

读完了全部机制，回到一个朴素的问题：**这套东西适合谁、不适合谁？** 本章不做功能罗列，只给判断框架。很多团队第一次接触"代码图"类工具时的误判，都来自把三件不同的事混为一谈：检索、导航、**审计**。这本书讲的是前两件。

## 一句话定位

CodeGraph 是一个**确定性提取的代码情报图**：把代码库的结构性关系（符号、调用、路由、继承）预先物化成一张可查询的图，主要消费者是 AI 编码 agent 和需要快速理解代码的人。它的所有设计取舍都服务于一个目标：**让 agent 在少数几次结构化查询之后，获得足以停止阅读源码的答案。**

它不是的东西，同样要说清：

- **不是审计级静态分析（SAST）**。没有污点分析、没有跨函数数据流追踪、没有漏洞规则引擎。它回答"谁调用了谁"，不回答"这段代码是否安全"。
- **不是编译器替代品**。tree-sitter 看到的是预处理之前的源文件，类型系统、宏展开后的真实代码它天然看不见。
- **不是语义搜索**。检索建立在标识符、驼峰拆词和图关系上；纯自然语言的模糊提问不是它的主场（见 CRG 对比章）。

## 适用的五类场景

1. **AI coding 的上下文供给。** 这是它存在的第一理由。agent 接到 flow 类问题（"X 怎么到达 Y"）时，一次 `codegraph_explore` 返回端到端路径 + 内联源码 + 接线点，取代原本 9–10 次 Read / 10–11 次 Grep 的手工拼凑（本书引言的实测数字）。
2. **代码导航与影响分析。** `getCallers` / `getImpactRadius` / `getTypeHierarchy` 回答"改这个函数会波及谁"，包含动态分发的合成边——这类边是 naive ctags + grep 方案给不出来的。
3. **大型仓库的 onboarding。** 新成员面对陌生仓库时，图的"先结构后细节"比从 README 或入口文件顺着读高效得多。实证章演示了这张图的查询手感。
4. **agentic 工具链的一环。** 作为 MCP 服务器挂进 Claude Code、Cursor、Codex 等 host；CLI 形态也可被任何脚本化 agent 直驱。安装器支持项目级/全局两种部署。
5. **多语言混合仓库。** 29 门语法、36 个框架 resolver，TypeScript/Java/Go/Python/C# 混在一起的 monorepo 能进同一张图、用同一套查询。新增语言的边际成本是"填一张配置表"。

## 已知边界（选型前请逐条过）

### 边界一：C/C++ 宏是系统性短板

tree-sitter 解析的是**未经预处理**的源文件。`TRACE_POINT(1)` 这样的宏调用在 AST 里就是个 call_expression，而宏展开后的真实代码（条件编译选中的分支、宏生成的函数体）对图不可见。本仓的对策是**保守抑制而非假装理解**：`cpp-macro-visibility.ts` 会识别"这个 calls ref 其实是宏展开"，然后把它丢掉——因为绑到同名函数上会捏造一条不存在的调用边（#1838）。

含义很直白：**在宏密集的 C/C++ 代码库上，CodeGraph 的图是不完整的——而且是有意不完整。** 它选择"少一点但不出错"（静默优于错边）。对 agent 检索场景这是正确取舍；对需要完整调用图做审计的场景，这是硬伤——后者需要编译器前端（构建捕获 + clang AST），详见下一章的分层讨论。

### 边界二：大仓库需要内存工程

开箱即用的默认配置面向常见规模的仓库。数百万行级、或符号极密的超大仓库，需要按本书性能章的机制做针对性调优：解析池大小（`CODEGRAPH_PARSE_WORKERS`）、Rust 内核的启用、WAL 阈值、worker 重建节奏。这些旋钮全部存在且经过实战打磨，但**"装完就丢给它一个巨型仓库"不是它的标称能力**——这与所有同类的开源代码索引工具相同，属于工程投入而非架构缺陷。

### 边界三：数据流在图外

局部的、不经过图边的数据流（比如"这个局部变量的值改了几步之后流到哪了"）不在覆盖范围内——本书多次出现的 Excalidraw 工作样例里，残留的 Read/Grep 全部属于这一类。跨函数污点分析（用户输入 → 危险函数）则需要规则引擎 + 数据流分析，属于另一个产品类别。

### 边界四：图是"当前构建"的快照

索引是按文件序确定性重建的，不是实时数据库。watch 机制让增量同步足够快，但 agent 拿到的答案总是"最近一次索引的世界"。对于高频改动的热区，注意 sync 的时机。

## 选型评估清单

给技术负责人一套可以直接回答的问题：

| 问题 | 倾向 CodeGraph | 倾向其他方案 |
|---|---|---|
| 主要消费者是谁？ | AI agent / 开发者自助导航 | 安全审计流水线、CI 合规门禁 |
| 核心诉求是什么？ | 检索提速、减少 agent 的 Read/Grep、理解代码 | 漏洞检出、污点路径、审计报告 |
| 语言构成？ | 多语言混合（尤其 TS/Java/Go/Python） | 宏密集 C/C++ 为主 → 需编译器前端 |
| 精度要求？ | "够用且可信，宁可少连不可错连" | "必须完整、必须可审计" → 需 SAST 引擎 |
| 仓库规模？ | 常见规模开箱即用；超大仓库可接受调优 | 期望零调优直跑超大仓库 → 需专门工程 |
| 部署约束？ | 本地优先、无云依赖、可挂 MCP | 需要 SaaS 化多租户服务 |

如果答案整列落在左侧，这本书剩下的部分值得你读完；如果右侧居多，下一章《工程借鉴》仍有价值——它讨论如何把 CodeGraph 的分层结构用作更大系统的一块积木。
